# 2026-07-14 Grasp G0a D344 — 13개 고정점 충돌 조각 적용과 새 프로세스 검증

이번 case의 신규 변수: `[attempt3_fixed_point_collision_geometry]`

상태: **종료 — `D344_G0A_ATTEMPT3_AUTHORING_CONTRACT_FAIL_STOP`**

## 1. 무엇을 왜 하는가

D339는 동일한 설정으로 두 번 만든 볼록 조각이 정확히 같음을 증명했지만,
Isaac이 실제 장면에서 만든 128개 충돌 조각 중 13개가 저장 형상과 달랐다.
D340은 그 13개가 한 번 더 생성되면 더는 바뀌지 않는 후보를 찾았지만, 서로 다른
좌표 표현을 해시로 비교해 전체 판정이 실패했다. D342는 올바른 좌표 비교를
13/13으로 증명했고, D343은 최소 두께 값의 자료형과 정확한 비트를 128/128로
증명했다.

D344는 이 세 하위 증거를 합쳐 새 자산 후보를 실제로 만든다. D339 자산을 직접
수정하지 않고 새 `attempt3` 폴더에 복사한 뒤, 미리 고정된 13개 조각만 한 번
교체한다. 이어서 완전히 새 프로세스에서 128개 실제 충돌 형상을 다시 만들고,
고정 목표 자세에서 원본 형상과 새 실제 충돌 형상이 모두 원통을 피하는지
확인한다.

## 2. 이번에 바꾸는 것과 바꾸지 않는 것

새 물리 변수는 하나뿐이다.

- `attempt3_fixed_point_collision_geometry`: D340에서 이미 정해진 13개 조각을
  하나의 고정된 수리 묶음으로 적용한다.

13개를 각각 별도 변수로 세지 않는다. 결과를 본 뒤 조각이나 값을 고르는 것이
아니라, 실행 전에 대상과 좌표가 모두 고정된 한 묶음이기 때문이다.

다음 값은 전부 동결한다.

- 한 조각의 꼭짓점 한도: 64
- 최대 볼록 조각 수: 64
- 분해 분석 격자 수: 1,000,000
- 분해 허용 오차: 1.0
- 최소 두께 요청값: 0.0001m
- 최소 두께 실제 float32 비트: `0x38d1b717`
- 원본 표면 밀착 기능: 켜짐
- 실제 형상과 저장 형상의 표면 차이 한도: 0.1mm
- 원본과 실제 충돌 형상의 목표 거리 차이 한도: 0.5mm
- 목표 자세: radial 7mm, tangent 11mm
- 열린 그리퍼: q5=1.5413rad (`q5=0`은 닫힘)
- seed: 33201

파라미터 증가, 파라미터 변경, 허용 기준 완화는 모두 0건이어야 한다.

## 3. 정확히 바꾸는 13개

- link5: `part_011`, `part_018`, `part_023`, `part_024`, `part_040`,
  `part_041`, `part_045`, `part_054`
- gripper_link: `part_000`, `part_035`, `part_036`, `part_048`, `part_057`

나머지 115개 조각은 좌표·삼각형 배열까지 D339와 같아야 한다. 질량, 무게중심,
관성, 소유 링크, 경로, 스키마, 비물리 파일도 그대로여야 한다.

## 4. 과거 실패를 지우지 않는 사용 자격 검사

D340과 D342의 전체 실패 표시를 참으로 바꾸지 않는다. 새 D344 사용 자격 파일은
다음 긍정 하위 증거만 독립적으로 연결한다.

1. D340: 두 생성 경로 결과가 13/13 같고, 고정점 후보가 13/13 존재한다.
2. D340에서 거짓이었던 항목은 서로 다른 좌표 표현의 해시 비교 하나뿐이다.
3. D342: 직접 저장 좌표·삼각형 확인과 몸체 좌표의 수치 확인이 13/13 통과했다.
4. D342의 유일한 별도 실패는 미등록 `1e-12m` 비교 기준이었다.
5. D343: 올바른 최소 두께 자료형·비트 계약이 128/128 통과했다.
6. 현재 사용자가 D344 자산 변경을 명시적으로 승인했다.

## 5. 실행 순서

### 5.1 첫 번째 프로세스 — 새 자산 만들기

1. D338-D343 입력 파일의 목록과 SHA-256을 봉인한다.
2. D339 attempt2를 D344의 새 attempt3 폴더로 복사한다.
3. 정확히 13개 조각의 `points`, `faceVertexCounts`, `faceVertexIndices`만 교체한다.
4. 13개가 후보 바이트열과 같은지, 115개가 D339와 같은지 다시 읽어 확인한다.
5. 나머지 물리층 의미, 질량·관성, 비물리 파일이 같은지 확인한다.
6. 128개 최소 두께 속성이 모두 `float`, authored 값, 정확한 비트
   `0x38d1b717`인지 확인하고 프로세스를 종료한다.

이 단계가 실패하면 불완전한 폴더를 증거로 보존하고 같은 경로에 덮어쓰지 않는다.

### 5.2 두 번째 프로세스 — 실제 충돌 형상 새로 읽기

1. 새 프로세스가 attempt3만 연다.
2. 각 128개 조각에서 prototype과 live instance 생성 요청을 별도로 수행한다.
3. 총 256개 callback 결과와 좌표를 판정 전에 파일로 남긴다.
4. 활성 64개+비활성 옛 충돌체 1개를 몸체별로 구분한다.
5. 활성 128개 전부에서 소유 링크, 단위 변환, GPU 호환성, 최소 두께 비트,
   표면 차이 0.1mm 이하, 부피 차이 5% 이하를 확인한다.
6. 바꾼 13개는 같은 몸체 좌표에서 다시 생성해도 더 줄어들지 않는지 확인한다.
7. 128/128이 통과한 경우에만 고정 `(7,11)mm`, q5=1.5413rad 자세에서
   원본과 실제 충돌체의 원통 거리를 비교한다.
8. 시뮬레이션 진행 횟수가 처음과 끝에 같은지 확인하고 종료한다.

## 6. Rerun 완료 계약

Rerun은 숫자 판정 도구가 아니라 공간 결과를 사람이 확인하는 기록 도구다. 해시와
거리는 callback 배열과 JSON이 권위다.

D344 기록에는 다음이 서로 구분되어야 한다.

- D339 원래 128개 조각
- D344 attempt3에 실제 저장된 128개 조각(바꾼 13개는 D340 후보와 바이트 동일)
- 새 live instance 128개
- 새 prototype 128개
- 원본 raw 충돌 메시 2개와 목표 원통
- 조각별 표면 차이, 부피 차이, 소유권, 활성 여부, 최소 두께, 최종 통과 여부
- 목표 좌표계와 실제 좌표계

종료 꼬리표, 정확한 항목·시간축·구성요소, 내장 화면 배치, 별도 `.rbl`, headless
화면 파일을 기계 검사한다. 그 다음 실제 화면 파일을 직접 열어 본 별도 기록을
남겨야 완료다. 화면이 실패해도 수치 결과를 바꾸지는 않지만 다음 사례 자격은 주지
않는다.

기존 `collision_gate` 화면은 좌표축을 기록해도 8개 메시 비교 패널에서 숨겼다.
D344 사전 등록에서는 각 패널의 내용에 `/frames/**`를 추가한다. 이는 목표·실제
좌표축을 보이게 하는 관측 화면 보강이며, 수치 판정·물리·분해 설정은 바꾸지 않는다.

## 11. 어디에서 왜 멈췄는가

마지막 “물리층 전체 의미 비교”가 거짓을 반환해 등록된 중단 규칙이 작동했다.
판정은 다음으로 보존한다.

`D344_G0A_ATTEMPT3_AUTHORING_CONTRACT_FAIL_STOP`

이 때문에 두 번째 새 프로세스 검증은 실행하지 않았다. 따라서 callback 256개,
실제 충돌 조각 128개 검증, 목표 자세 거리 확인, Rerun 기록, 화면 파일, 물리
settle은 모두 생성되지 않았다. 같은 출력 폴더에 자산 생성 명령을 다시 실행하지
않는다.

중요하게도, 실패한 것은 다음 한 항목뿐이었다.

- 등록한 39개 좌표·삼각형 속성을 가린 뒤, USD 장면의 모든 항목을 문자열로
  바꿔 만든 해시가 원본과 같은가: 실패

반면 다음 검사는 통과했다.

- 물리층에서 등록한 39개 속성을 실제로 제거한 두 파일의 전체 내용: 동일
- 장면 항목 경로 310개와 개수: 동일
- 물리층 머리말: 동일
- 39개 허용 속성의 정확한 목록: 동일

## 12. 사후 원인 분해 — 실제 자산 차이인가, 비교기 오류인가

자산은 수정하지 않고 원본과 attempt3를 읽기만 하는 진단을 서로 독립된 두
프로세스에서 실행했다. 실패한 비교기의 행 생성 방식을 그대로 재현한 다음,
어느 필드가 다른지 하나씩 분해했다.

결과는 다음과 같다.

- 비교한 USD 장면 항목: 310개
- 원래 해시에서 다르다고 나온 항목: 194개
- 194개 모두에서 달랐던 필드: `apiSchemas` 메타데이터 하나
- 좌표, 삼각형, 속성값, 연결 관계, 경로 등 다른 차이: 0개
- 메모리 주소가 아닌 차이: 0개

`apiSchemas`는 “이 장면 항목에 어떤 기능 묶음이 적용됐는가”를 적는 USD
메타데이터다. 비교 코드는 그 값을 내용으로 직렬화하지 않고 파이썬 객체의
`repr(...)` 문자열로 바꿨다. 이 문자열에는 실행 중 임시 메모리 주소가 들어간다.
주소는 자산 내용이 아니며 프로세스마다 달라진다.

실제로 첫 진단과 두 번째 진단의 주소 포함 원본 해시는 서로 달라졌다. 반면
`<pxr.... object at 0x...>` 형태의 실행 주소만 제거하고 다시 계산한 해시는 원본과
attempt3, 첫 실행과 두 번째 실행 모두 정확히
`1e458982f356a6d546b73631abf133d302e0371f9a898eae674f76e65f82f9fe`였다.

따라서 이번에 관찰한 실패는 등록한 39개 속성 밖의 실제 자산 차이를 증명하지
못한다. 비교기가 실행 중 주소를 자산 의미로 오인한 거짓 차이다. 그러나 이 결론을
이용해 D344를 소급 PASS로 바꾸지는 않는다. 등록된 비교기가 실패했으므로 D344의
공식 판정은 계속 실패 정지다.

## 13. Rerun을 실행하지 않은 이유

D344의 Rerun은 두 번째 새 프로세스가 실제 충돌 형상 128개를 만들고 판정할 때
실행하도록 사전 등록했다. 첫 번째 자산 생성 단계가 실패하면 두 번째 단계 자체를
금지했다. 따라서 이번에는 Rerun이 필요 없어서 임의로 생략한 것이 아니라, Rerun이
기록해야 할 실제 검증 장면에 도달하지 못해 실행하지 않은 것이다.

이는 D341 계약의 완료를 주장하는 것이 아니다. D344에는 완료된 RRD·RBL·화면
파일·별도 육안 확인이 없으며, 다음 실제 형상 검증 사례가 허가되면 D341 전체
절차를 다시 수행해야 한다.

## 14. 파라미터를 늘렸는가

아니다.

- 신규 변수: 1건
- 기존 파라미터 증가: 0건
- 기존 파라미터 변경: 0건
- 허용 기준 완화: 0건
- 분해 설정 변경: 0건
- 목표 자세·q5·seed·IK 변경: 0건
- 물리 파라미터 변경: 0건

동결값은 꼭짓점 한도 64, 최대 조각 64, 격자 1,000,000, 오차 1.0,
최소 두께 0.0001m, 원본 표면 밀착 켜짐 그대로다.

저수준 작성 함수가 남긴 `d340_attempt3_asset_manifest.json`에는 D340 당시 함수가
사용하던 두 계약 이름이 계보 정보로 들어 있다. 이것은 D344에서 추가한 두 변수가
아니다. D344의 범위 권위 파일인 사전 등록, 파라미터 감사, 바깥쪽 attempt3
manifest는 모두 새 변수 한 건을 기록한다. 실제로 바뀐 물리 항목도 사전 고정한
13개 형상 묶음 한 건뿐이다.

## 15. 일상어 판정과 다음 연구

이번에 만든 새 충돌 자산 후보는 “13개만 바꾸고 115개를 그대로 보존한다”는 핵심
작성 검사를 통과했다. 하지만 전체 파일 비교기가 실행 중 메모리 주소를 파일
내용으로 착각해 중단됐다. 그래서 새 자산이 Isaac에서 실제로 더 정확한지는 아직
시험하지 않았다.

가장 좁은 다음 사례는 D345 `결정적인 USD 메타데이터 비교기 수리`다. D344의
attempt3를 수정하지 않고 읽기만 하며, `apiSchemas`를 메모리 주소가 아닌 실제
토큰 목록으로 직렬화해 두 독립 프로세스에서 같은 결과가 나오는지 증명해야 한다.
이 증명 사례에서는 자산 변경, Isaac 실행, Rerun, 물리 진행을 하지 않는다.
D345가 통과한 뒤에만 별도 사례에서 D344 attempt3의 새 실제 충돌 형상 128개와
Rerun 완료 계약을 검증한다.
